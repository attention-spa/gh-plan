# Security baseline and scanner posture

**Scope:** `attention-spa/gh-plan` (public GitHub repository). **Checked:** 2026-11-17. This is a security visibility and CI policy, **not npm publication approval**. Live settings can change; reread the endpoints before subsequent release decisions.

## Current enforced baseline

- An npm v3 lockfile pins direct and transitive dev dependencies with integrity values. Both PR and trusted-main worker use `npm ci --ignore-scripts --no-audit --no-fund` (not `npm install`), and verify the manifest/lockfile did not drift.
- The **read-only GitHub-hosted Node 24 `consumer-node24` job**, triggered for both `pull_request` and `main` pushes, runs **`npm audit --package-lock-only --audit-level=moderate`** on the complete committed lock (including dev dependencies). This requests current registry advisories, fails CI on moderate-or-higher findings, and cannot update dependencies. Registry/transport failures are not silently treated as a clean audit. `--no-audit` in `npm ci` avoids the installer running a duplicate implicit audit; it does **not** suppress the explicit gate.
- Full PR contracts execute on GitHub-hosted Node 22 with `contents:read`. The hosted Node 24 audit has the same read-only permission. The trusted main-controller retains its existing narrowly scoped Actions-dispatch permission; the worker prefers `[self-hosted, Linux, trusted]` only for immutable, verified `main` commits. **No untrusted PR code or live registry scan is moved to the OCI worker.**
- The audit is a **known-advisory gate**, not proof that the code, dependencies, or registry are vulnerability-free.
- **CodeQL default setup enabled in [#214](https://github.com/attention-spa/gh-plan/issues/214)**, with the default query suite, `remote` threat model, and standard GitHub-hosted runner. The owner-approved REST request selected `actions` and `javascript-typescript`. GitHub manages the scanning workflow; no custom CodeQL workflow YAML, OCI job, package runtime code or token/credential change was needed. The first [CodeQL setup run](https://github.com/attention-spa/gh-plan/actions/runs/44076006823) succeeded for **both** languages on `main` commit `96615871`, using only `ubuntu-latest` in the GitHub Actions runner group. The readback reports `configured`, `schedule: weekly`, `runner_type: standard`, `query_suite: default`; the language field may include aliases (`javascript` / `typescript`) while the analyzed categories are the canonical `actions` and `javascript-typescript`. This live check complements, not replaces, the 2026-11-17 exact-version review and prior 0-vulnerability npm audit recorded under [#202](https://github.com/attention-spa/gh-plan/issues/202).

## R2.1 repository-default GitHub Actions token scope (#223)

**Enabled and independently verified 2026-11-17:** The repository-level `GITHUB_TOKEN` default is now **read-only**, changed from `write` with one scoped GitHub REST `PUT /repos/attention-spa/gh-plan/actions/permissions/workflow`, and independently confirmed by a GET. The unrelated `can_approve_pull_request_reviews: true` setting was **preserved** rather than silently changed. This is a defense-in-depth default, not a substitute for source protection or review policies; a trusted author can still explicitly request wider job permissions in workflow YAML, subject to repository/organization policy.

All four committed workflow definitions explicitly limit their own token permissions. Hosted PR `contracts` and `consumer-node24` jobs use `contents:read`; trusted `main` and manually dispatched bootstrap controllers explicitly request **`actions:write`** only to dispatch/check worker runs. The `[self-hosted, Linux, trusted]` workers keep `contents:read` (bootstrap additionally `issues:read`). The controller's explicit grants are not removed by the new repository default. No org-wide setting, Actions policy, default branch, workflow YAML, runner, package publication, or credential was changed.

**R2.2 now enforces PRs and hosted checks on `main`** under the active ruleset described below. Mandatory independent human reviews remain **0** pending owner review-policy choice, release tag protections remain undecided, and `allowed_actions:all` / `sha_pinning_required:false` are unchanged. Do not mark full R2 complete until those remaining governance and release-environment requirements are explicitly addressed.

## R2.2 active main-branch PR and hosted-check ruleset (#225)

**Implemented and verified 2026-11-17:** GitHub public-repository Free organization ruleset [`27459624`](https://github.com/attention-spa/gh-plan/rules/27459624) is **active** for **only** `refs/heads/main`. An independent `GET /rules/branches/main` returned all four effective rules and `GET /branches/main` now reports `protected:true` (classic `protection.enabled:false` because this is a **ruleset**, not a classic branch-protection rule).

| Rule | Enforced behavior |
| --- | --- |
| `pull_request` | All changes to `main` must arrive through a PR; required approving reviews **0** to preserve the existing agent PR/CI/squash-merge workflow. Existing `merge`, `squash`, and `rebase` options are retained. Zero reviews **does not** imply independent review was performed. |
| `required_status_checks` | The hosted PR `contracts` and `consumer-node24` GitHub Actions checks must pass; both checks pin `integration_id:15368` (verified GitHub Actions App). A `strict_required_status_checks_policy:false` first-stage rule avoids forcing automatic rebase for every PR; source updates may still require reruns. Do not require GitHub-managed CodeQL default checks on fork-origin PRs, where CodeQL may not run. |
| `deletion` and `non_fast_forward` | Prevent deletion of or force-push rewriting of `main`. |
| `bypass_actors: []` | No actor-specific ruleset bypass is granted, including to the agent identity. Ruleset administrators can still modify the ruleset itself; that governance authority should be audited separately. |

**Remaining decisions:** Whether a human/independent approval must be required (which would block autonomous agent merges without another eligible reviewer), stale-branch strictness, Actions third-party allowlists/SHA pinning, release-tag creation/update/deletion protections and release environment gating. **R2 release acceptance remains unchecked.** Existing repository-default `GITHUB_TOKEN:read`, trusted main/OCI runner isolation, CodeQL, secret controls and package publication restrictions are unchanged. Future ruleset edits must verify the effective rule contract and successful normal PR merging before reporting completion.

## R6 policy — free-first, capability-based security visibility (#219)

**Decision (2026-11-17):** Required security outcomes must not depend on purchasing GitHub Team, Enterprise or paid Code/Secret Protection licenses. Choose the strongest **available, no-additional-license** controls for the repository's actual visibility and plan; verify them with live settings/readbacks and documented finding triage. If a native feature is not available, use reasonable, documented compensating controls and record the residual limitations and owner acceptance. This is an R6 *security-visibility policy*, not a blanket assurance that a package is safe or a license to publish.

| Capability | Public repository on GitHub Free | Private repository in a GitHub Free organization |
| --- | --- | --- |
| Dependency advisories | GitHub Dependabot alerts plus reproducible lockfile, hosted CI `npm audit`; address actionable alerts. | Dependabot alerts and CI `npm audit` remain available; audit scope and evidence must be recorded. |
| Static code scanning | Free hosted CodeQL (for supported languages) with analysis results and findings triaged. | Native CodeQL advanced security features generally require paid entitlement; use appropriate free hosted CI/static-analysis alternatives or documented risk acceptance. |
| Secret detection | Free **repository secret-scanning user alerts**, distinguish from the separate automatic public partner/provider scan. | GitHub Secret Protection user alerts require a paid eligible plan; use a maintained CI scanner (e.g. Gitleaks), scoped credentials and documented false-positive handling. |
| Prevent committing credentials | Free **repository-level push protection** when enabled for public repo. Record bypass policy and response; not a substitute for rotation. | Native repository push protection is unavailable without paid Secret Protection. Use local pre-commit/pre-push hooks for early warnings and CI checks for detection; hooks can be bypassed and CI cannot block the initial push. |
| Governance/provenance | Repo branch protections, required checks, trusted release provenance are separately decided in R2/R4. | Same separation; do not claim a scanner substitutes for protections, PR review, least-privilege credentials or signed release provenance. |

**Baseline for this public repository:** GitHub's own [recommended minimum](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-security-and-analysis-settings-for-your-repository) includes Dependabot alerts, secret scanning, push protection and code scanning. R6.1 hosted npm audit and CodeQL default setup are already operational and the original five CodeQL alerts were remediated. User-facing secret-scanning alerts and repository push protection were **enabled and verified** in a separate [#221](https://github.com/attention-spa/gh-plan/issues/221) settings unit. The observations below record the enabled state. No feature enablement or paid-plan change was performed under policy issue #219. Public partner scans and user-level push protection do **not** prove these two repository-level controls are enabled.

**Release-check acceptance:** Record the public/private eligibility, live feature state, active advisory/CodeQL/secret alerts and their disposition, effectiveness/limits of any alternative scanner, notification/incident and bypass procedures, and residual risk. **Do not require a paid upgrade merely to check R6.** R6 can be marked complete once appropriate available controls (or approved alternatives) and actionable findings are independently verified. R1 destination/ownership, R2 protected source and tags, R4 trusted publishing/provenance, release documentation and final owner authorization remain separate unchecked gates. The change in this issue updates policy only; publication remains forbidden.

## Recommended next controls — separately authorized work

1. **CodeQL default setup is enabled and the initial findings were remediated.** [#214](https://github.com/attention-spa/gh-plan/issues/214) enabled hosted JS/TS + Actions scanning; [#215](https://github.com/attention-spa/gh-plan/issues/215) implemented parsed-origin validation, redirect rejection and more precise test assertions through [PR #217](https://github.com/attention-spa/gh-plan/pull/217), merged as `2ae49f96`. All five original high-severity alerts are independently `fixed` after a main-branch CodeQL rescan, not dismissed. Continue monitoring. Default setup excludes fork-origin PRs; CodeQL-managed permissions are separate from read-only PR CI. Requiring CodeQL checks for merges needs owner-approved R2 governance.
2. **Secret scanning and repository push protection are enabled on this public repo** through [#221](https://github.com/attention-spa/gh-plan/issues/221). Operational response: review new user alerts and bypass events promptly; for a genuine credential, **revoke/rotate it at its provider before resolving the alert**, inspect downstream access and remove the committed value where appropriate. Allow a push-protection bypass only for a verified false positive or documented non-sensitive test value, with named owner and reason. Monitor GitHub repository security notifications/appropriate watchers; do not assume a bespoke on-call route or custom validity checks are configured. Capture the inaccessible scan-history limitation; never generate a live or fake credential merely to test detection. This does not enable private/org-wide settings, AI detection, additional secret patterns, billing or Dependabot security-update PRs.
3. **Enable Dependabot security updates** only after an owner decision on bot PR volume, repository/organization settings, workflow-trigger boundaries, pinned dependency overrides and review policy. Empty Dependabot alerts **do not** prove that updates are configured. Optional `.github/dependabot.yml` scheduling for version updates is a separate decision.
4. **SBOM:** consider an explicitly generated/tested CycloneDX/SPDX artifact if required for release provenance. The 404 GitHub endpoint does not justify fabricating an SBOM. Supply-chain provenance/OIDC release configuration belongs to #202 R4 and requires publication architecture approval.
5. **Source governance:** protect `main`, require checks/reviews, constrain allowed actions/SHA pins, tag/release environments and default Action tokens only in the separately authorized **R2** unit. A security audit's presence is not a substitute for enforced branch protection.
